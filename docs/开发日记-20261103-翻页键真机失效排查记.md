# 开发日记｜wsstunnel 翻页键"点击无反应"排查记：三次测量，三个真因

**日期：2026-11-03**
**项目：wsstunnel（WebSocket 反向 Shell 中继）　版本：v1.0.12 → v1.0.13 → v1.0.14**
**涉及文件：`wsstunnel/web/index.html`、`wsstunnel/relay.py`、`tests/test_web_ui.py`**

---

## 一、起点：一句被问了很多次的话

> "page up page down 按钮为何一直失效，点击无反应，仔细看看，帮我修复。"

这不是第一次被问了。翻回 `git log`，同样的问题已经修过四轮：

| 版本 | 当时的判断 | 改动 |
|---|---|---|
| v1.0.7 | 真机手势被浏览器抢走 | `touch-action:none` 直接覆盖 `.xterm-viewport` |
| v1.0.8 | 开会话面板太麻烦 | 主球上下新增半透明 ▲/▼ |
| v1.0.10 | `div + click` 在 iOS/微信 X5 上不可靠 | 改成 `<button>` + `pointerdown` |
| v1.0.12 | 元素级事件被 X5 吞掉 | 热区 40→48px、document 级 touchstart 坐标兜底 |

每一轮提交信息里都写着"本地实测通过"：按钮中心、上方 30px、左侧 30px 都能翻页。可真机上就是不动。

到 v1.0.12 这一版，用户已经把"按钮位置、热区大小、事件类型"这三条路都堵死了。继续沿着"事件没绑上"的方向猜，大概率是第五次白改。所以这次我先做了一件前四轮都没做的事：**不写代码，先量数据。**

## 二、第一次测量：点击究竟落在了谁身上

"点了没反应"在工程上只有两种可能：

1. 事件根本没到按钮上；
2. 事件到了，但翻页动作是空操作。

这两条路对应的修法完全相反——前者调热区/事件类型，后者要查终端状态。先把它分开。

浏览器打开页面、接上真实 relay 和后端、`seq 1 200` 灌出足够长的回滚历史，然后不打字，直接问 DOM：

```js
document.elementFromPoint(▲按钮中心.x, ▲按钮中心.y).id
// → "fab"
```

一句话结案：**点击确实发生了，但落在 ⌨ 主球上，不是 ▲。**

## 三、第二次测量：为什么只有真机才撞上

既然点击被 ⌨ 抢了，下一个问题自然是"两个按钮怎么会叠在一起"。量一下桌面浏览器的几何：

```
视口 1280×779：        ▲ 在 558–606      ⌨ 在 398–446     相隔 150px
```

分得清清楚楚——这就是前四轮"本地实测通过"的原因。差异不在浏览器，在**键盘**：手机上的终端页，输入焦点常驻 textarea（`ws.onmessage` 里还会主动 refocus），软键盘几乎一直弹着，可视高度从 844 掉到 500 上下。

于是把视口高度当成变量，一档一档量 `getBoundingClientRect()` 和 `elementFromPoint()`：

| 可视高度 | ▲ 位置 | ⌨ 位置 | `elementFromPoint(▲中心)` |
|---|---|---|---|
| 844px（键盘收起） | 558–606 | 398–446 | `page-up` ✅ |
| 700px | 414–462 | 326–374 | `page-up` ✅ |
| 600px | 314–362 | 276–324 | `page-up` ✅ |
| **520px（键盘弹起）** | **234–282** | **236–284** | **`fab`** ❌ |
| 460px | 174–222 | 206–254 | `page-up` ✅（错位） |

真相在 520px 这档：两个 48px 的圆几乎完全重合，而 ⌨ 的 `z-index` 是 40、▲ 是 39。**手指点下去，全归 ⌨。**

根因是页面里那段"键盘弹出时固定 FAB 位置"的胶水代码：

```js
function fixPos() {
  const vv = window.visualViewport;
  const midY = vv.height / 2;
  fab.style.top = (midY - 24 + vv.offsetTop) + 'px';   // ⌨ 顶到可视区正中
}
```

它只搬了 ⌨，而 ▲ 是 `position: fixed; bottom: 238px`——两者各自"贴着可视区"，可视区一缩就必然相撞。这不是概率问题，是几何必然。

## 四、修复一（v1.0.13）：让它们物理上不可能重合

修法不是调 z-index、也不是再扩热区（那只会把"点不中"变成"点中错的"），而是**取消三个键各自定位的权利**：

```html
<div id="fab-group">        <!-- 整组定位 -->
  <button id="page-up">▲</button>
  <button id="fab">⌨</button>
  <button id="page-down">▼</button>
</div>
```

```css
#fab-group {
  position: fixed; right: 12px;
  display: flex; flex-direction: column; gap: 10px;   /* 内部排布，永不重叠 */
  pointer-events: none;                                /* 容器不挡终端 */
}
#page-up, #fab, #page-down { pointer-events: auto; width: 48px; height: 48px; }
```

顺手修掉的三个隐藏问题：

- **节流是全局的**：`_pageFireAt` 全页共用一个 300ms 窗口，先点 ▲ 再点 ▼ 会被吞掉。改成 `_fireAt[key]` 每键 180ms。
- **xterm 版本没锁**：`cdn.jsdelivr.net/npm/xterm/lib/xterm.js` 不锁版本，一旦拿到 4.x，`term.buffer.active` 直接抛 `TypeError`——异常被事件处理器静默吞掉，表现又是"点了没反应"。锁定 `xterm@5.3.0`，并加 `activeBuffer()` 兼容层（`term.buffer.active || term.buffer`）。
- **键盘开合会重置视口**：`term.resize()` 后 xterm 把视口拉回底部，刚点 ▲ 翻上去的内容"弹"回来。改为重排后保留视口顶端行号。

实测（390 宽，5 档高度，每档连点两次 ▲ 再点 ▼）：

```
844px  ▲: 156→106→56   ▼: 106   三键 elementFromPoint 各自正确
600px  ▲: 171→136→101  ▼: 136
520px  ▲: 176→146→116  ▼: 146   ← 旧版这里被 ⌨ 吃掉
460px  ▲: 180→154→128  ▼: 154
380px  ▲: 185→164→143  ▼: 164
```

发版 v1.0.13、打 tag、推送，并从 GitHub tag 装到腾讯云的 t 机（`wsstunnel-relay` / `wsstunnel-client` 两个 systemd 服务），`systemctl restart` 后页面 200、外网 `https://yuangs.cc/wstunnel` 也拿到新版。

**然后用户回来了：还是不动。** 而且这次有一句非常关键的信息——

> "点击下箭头，显示到底了，点击上箭头，显示到顶了。"

## 五、第三次测量：能点中，却一动不动

"到顶了"和"到底了"同时出现，在逻辑上只有一个解释：**终端认为自己既在顶部又在底部**，也就是 `viewportY === 0 === baseY`——没有可回滚的行。但用户说页面上输出很多。

xterm 的内部状态是唯一的裁判，直接把三件事打出来：

```js
term.buffer.active.baseY       // 0
term.buffer.active.type        // "alternate"
term.options.scrollback        // 1000（有，但备屏不适用）
```

`alternate`——**终端处在备屏**。备屏是 vim / less / tmux / top 这类全屏程序用的第二块画布，内容由远端程序自己管，`baseY` 恒为 0，浏览器本地翻页本来就是空操作。旧逻辑在这种情况下只做了一件事：

```js
if (bufferType() !== 'alternate') {
  const moved = scrollPage(...);
  if (!moved) pageHint('top' / 'bottom');   // 只弹提示，从不发给远端
  return;
}
```

所以「上箭头→到顶了、下箭头→到底了」其实是这段代码在正确地报告"本地翻不动"，只是它**没把翻页键转发给远端**——于是 tmux 里几百屏的内容，一个键都翻不到。

还有一个放大器：xterm 4.x 没有 `buffer.type` 字段，`bufferType()` 会返回 `'normal'`，**连备屏判断都失效**，直接走进本地翻页分支，症状一模一样。

## 六、修复二（v1.0.14）：让"翻不动"有出路

核心是一句话：**本地真能翻才本地翻，翻不动就交给远端。**

```js
function canScrollLocally() {
  const b = activeBuffer();                 // 5.x 的 .active，4.x 退回 buffer 本体
  if (!b) return false;
  if (b.type === 'alternate') return false; // 备屏：归远端
  return (b.baseY || 0) > 0;                // 没有回滚行：也归远端
}
```

```js
if (canScrollLocally()) {
  if (scrollPage(dir)) return;              // 本地翻成功，不打扰远端
  pageHint(dir < 0 ? 'top' : 'bottom');     // 真到边界了
  return;
}
// 备屏 / 无回滚历史 → 回退成发送 ESC[5~ / ESC[6~
bytes = dir < 0 ? [0x1b, 0x5b, 0x35, 0x7e] : [0x1b, 0x5b, 0x36, 0x7e];
```

三种情况都验证了一遍：

| 场景 | 行为 | 实测 |
|---|---|---|
| 正常缓冲、有历史 | 本地翻，不发字节 | `72 → 22 → 72` |
| 备屏（tmux/less/vim） | 发 `ESC[5~`（`27,91,53,126`） | 远端翻页，不弹错误提示 |
| 正常缓冲、无历史 | 发 `ESC[5~` + 提示"当前没有可翻的历史，已发给远端" | 文案准确 |

裸 bash 收到 `ESC[5~` 会被 readline 忽略，所以"无历史也发"没有副作用；这是关键取舍——**宁可多发一个无害的按键，也不要让用户看着屏幕干瞪眼。**

同一个用户还提了第二条要求：

> "位置请保持在原来的悬浮球的位置，在中间的位置，否则会被键盘遮挡，影响使用。"

v1.0.13 把整组钉在了 `bottom: 88px`，键盘一弹就压住。改回**屏幕垂直中央**，并按 `visualViewport` 实时重算：

```js
const gh = group.offsetHeight;                 // 164 = 3×48 + 2×10
group.style.top = Math.round(base + (vv.height - gh) / 2) + 'px';
```

实测 5 档高度，组中心恒等于屏高一半（422/300/250/210/180），三键不重叠、命中正确、整组始终可见。

## 八、复盘：五条写进清单的教训

**一、先分诊，再修。**"点了没反应"必须先区分"事件没到"和"动作空转"。前四轮全部押在第一种，所以每次都在调事件类型和热区。一次 `elementFromPoint` 就把方向翻过来了——**测量比猜测便宜两个数量级**。

**二、真机条件要在浏览器里重建。** 这个 bug 的真机独占变量是"软键盘占掉 40% 视口"。桌面和 DevTools 模拟器默认没有键盘，可视高度恒为 844，怎么测都测不出来。把视口高度做成 844/700/600/520/460 五档去量，第三次就撞见了。**"本地实测通过"这句话，必须能回答"本地和真机差在哪"**。

**三、报错/提示要为定位服务。** 如果当初提示的是"备屏，已转发给远端"而不是笼统的"已到顶部"，这一轮可能就不用问了。提示语现在区分了"真的到边界"和"本地没历史，已发给远端"。

**四、能本地解决不代表只能本地解决。** 在备屏里，浏览器本来就不该翻——正确的动作是**转发按键**。旧代码在"不是备屏"的分支里 return 得太早，等于放弃了远端这条正确路径。

**五、把结论固化成测试。** 这个 bug 修了四轮还在，根本原因是没有任何一条断言守着它。`tests/test_web_ui.py` 现在明确写着：三个键必须在同一个容器里、不许再被 `visualViewport` 顶到中央、必须保留回退发键、`scrollback` 必须显式设置、页面版本号必须与 `pyproject` 一致。**凡是嘴上说"这次真修好了"的地方，都该有一条会变红的测试。**
